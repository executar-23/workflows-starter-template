# Why Handoff

[English](why-handoff.md) | **한국어**

코딩 에이전트와 어느 정도 규모 있는 코드베이스에서 페어링해본 적이 있다면, 이 플러그인이 없애려는 마찰을 이미 느껴봤을 것입니다. 이 글은 README 피치의 긴 버전 — 왜 plan → execute → verify 라는 엄격한 핸드오프를 중심으로 짠 4개의 작은 스킬이 에이전트 보조 작업을 측정 가능한 수준으로 덜 고통스럽게 만드는지에 대한 논거입니다.

## 세 가지 실패 패턴

**같은-컨텍스트 맹점.** 같은 채팅 세션이 작업을 계획하고, 코드를 작성하고, 그것을 스스로 리뷰하면, 그 리뷰는 구조적으로 흠결이 있습니다. 방금 "이 접근법이 옳다"고 주장한 에이전트에게 "이 접근법이 옳은가?"를 물으면, 같은 mental model에서 답이 나옵니다 — plan을 만든 그 model입니다. 실제 예시: 에이전트가 `UserService`를 세 모듈로 쪼개는 리팩토링을 계획합니다. 깔끔하게 실행하고, verify를 시키면 모듈도 좋고 import도 풀리고 테스트도 통과한다고 확인합니다. 놓치는 건 — plan이 한 번도 언급하지 않은 상위의 `AdminController`가 여전히 옛 형태를 import하고 있다는 사실. 그 파일은 planning 중에 열린 적이 없어서입니다. 같은 diff를 새 채팅이 보면 누락된 wiring을 몇 초 안에 잡아냅니다 — plan이 옳다는 데 아무 이해관계가 없으니까요.

**프로젝트에 묶인 워크플로우.** Project A에서 에이전트와 일하는 리듬을 만들어둡니다 — 티켓 쓰는 방식, 검증해야 할 항목 체크리스트, 코드 요청 전 관련 컨벤션 문서를 인용하는 습관. Project B로 옮기면 그중 무엇도 살아남지 못합니다. 패턴은 누구도 다시 재생할 수 없는 채팅 기록 속에 흩어진 turn으로만 존재합니다. 처음부터 다시: 테스트 철학을 다시 설명하고, 타입에 얼마나 엄격한지 다시 정립하고, 어느 명령이 린터를 돌리는지 다시 발견합니다. 6개월 뒤에는 세 번째 프로젝트에서 같은 가르침을 반복합니다. 워크플로우는 진짜였지만 implicit이었고, implicit한 워크플로우는 이전(migrate)되지 않습니다.

**매번 다시 설명하는 컨벤션.** 새 채팅마다 같은 보물찾기로 시작합니다. 코딩 컨벤션이 어디 있죠? 테스트 명령은 뭐죠? 어느 디렉토리에 기능 문서가 있죠? 이게 pnpm workspace인가요 single package인가요? 에이전트는 알 수 없습니다 — 세션 간 기억이 없으니 — 그래서 묻거나(느림) 추측합니다(더 나쁨). 결국 새 대화마다 같은 세 단락의 컨텍스트를 붙여넣게 됩니다. 채팅당 비용은 작지만 분기 단위로는 막대하고, 그 반복성이 특히 사람을 지치게 합니다: 실제로는 변하지 않은 상태를 다시 세우려고 비용을 지불하고 있는 셈이니까요.

## 핸드오프가 고치는 것

**디스크 기반 상태.** 각 단계가 출력물을 `.handoff/*.md`에 씁니다. `verify`는 `plan.md`와 `task.md`를 디스크에서 읽습니다 — 그것을 만든 채팅과 메모리를 공유하지 않습니다. `/verify`를 새 채팅에서 돌리는 게 핵심입니다: 리뷰어는 plan이 옳다는 사전 commitment 없이 도착해서, 작성된 plan만 봅니다. 공유할 컨텍스트 자체가 없으니 같은-컨텍스트 맹점이 사라집니다.

**Stack-agnostic boundary.** `plan`이 plan에 들어갈 명령을 `config.md`에 기록된 toolchain을 읽어 결정합니다. `execute`는 plan이 말한 대로 기계적으로 따릅니다. 스킬 자체는 pnpm, Cargo, Django, Go module에 대해 아무것도 모릅니다 — 오직 boundary만 압니다: planner는 명령을 쓰고, executor는 실행하고, reviewer는 검사한다. 프로젝트별 지식이 스킬 prompt가 아닌 `config.md`에 살기 때문에, 같은 4개 스킬이 어떤 언어/프레임워크에서도 작동합니다.

**한 번 캡처되는 컨벤션.** `setup-handoff`은 프로젝트당 한 번 실행되어 새 채팅마다 묻던 것들을 스캔합니다: 에이전트 가이드 파일, manifest scripts, 문서 디렉토리, toolchain marker. 결과는 `.handoff/config.md`에 들어갑니다. 이후의 모든 `/plan`, `/execute`, `/verify`가 그 파일을 읽습니다. 채팅 경계마다 프로젝트를 다시 설명할 필요가 없어집니다 — 설명이 디스크에 있으니까요.

## 이게 아닌 것

- **프로세스 프레임워크가 아닙니다.** Spec-Kit, BMAD, GSD 같은 것들은 전체 lifecycle을 강요하고 그 안에서 살라고 요구합니다. 이 플러그인은 상황에 따라 호출하는 4개의 작은 스킬입니다. 한 줄 수정에 plan을 건너뛰고 싶다면, 막는 게 없습니다.
- **테스트 러너가 아닙니다.** `verify`는 `config.md`에 이미 있는 명령을 그대로 돌립니다 — 기존의 `pnpm test`, `cargo test`, `pytest`. 여기서 테스트 scaffolding을 제공하지 않습니다.
- **LLM이나 에이전트가 아닙니다.** markdown + 플러그인 manifest일 뿐입니다. 일은 기존 코딩 에이전트가 합니다; 스킬은 그 작업이 들어맞을 공유 shape를 줄 뿐입니다.

## 단계를 건너뛸 때

핸드오프에는 오버헤드가 있습니다. 오버헤드가 값할 때 쓰고, 그렇지 않으면 건너뜁니다.

- **diff가 명백한 단일 파일 리팩토링:** `plan` 건너뛰세요. 그냥 파일 수정하고 fresh-eye 검사를 원하면 `/verify`만 돌리면 됩니다.
- **버려질 프로토타이핑:** 전체 파이프라인 건너뛰세요. 오후 한나절보다 오래 살 코드에 아껴두세요.
- **핸드오프가 값을 하는 시점**은 변경이 3개 이상 파일에 닿거나, 원래 추론을 더 이상 쓸 수 없는 새 채팅에서 결과를 검증하고 싶을 때입니다.

## 마법은 어디에 없는가

이 플러그인은 일하는 패턴을 인코딩합니다. 에이전트를 더 똑똑하게 만들지 않고, 나쁜 plan을 구해주지 않으며, `verify`가 들여다볼 생각을 못한 것을 잡아내지도 않습니다. 더 나은 결과를 만드는 것은 plan과 execute와 verify를 분리하는 규율 자체입니다 — markdown 파일과 슬래시 명령은 그 규율을 따르기 쉽게 해주는 scaffolding일 뿐입니다. 이미 단계 사이를 수동으로 엄격히 핸드오프하고 있다면, 이 플러그인은 이미 하고 있는 것을 패키징한 느낌일 겁니다. 그렇지 않다면, 그 패키징이 핵심입니다.
